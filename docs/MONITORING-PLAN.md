# Моніторинг: аналіз і план доробок

Дата: 2026-09-19. **Статус: пропозиція для перегляду, зміни функціоналу ще не реалізовані.** Аналіз локального коду; без запуску робочих перевірок, відправлення Telegram чи налаштування хостингу.

## 1. Потреба користувача

При додаванні та редагуванні сайту потрібен зрозумілий вибір:

- **Лише моніторинг:** регулярні перевірки, статистика й сповіщення; без віддаленого вимкнення.
- **Моніторинг і керування:** ті самі перевірки плюс наявний механізм віддалених команд.

Потрібні вибраний список автоматично контрольованих сайтів, зрозумілі звіти за дні/тижні/місяці/весь період, доступність, тривалість збоїв, швидкість відповіді, повідомлення про падіння й відновлення.

## 3. Виявлені обмеження

1. **Два режими вже мають основу, але не оформлені як явний вибір.** Окремого monitoring_enabled немає: всі Prod потрапляють в обхід. site_type та environment не слід використовувати як заміну режиму керування.
2. **Відсоток не вимірює час.** Формула зараз: successful / (checks − planned). UI чесно називає це успішними перевірками; змінна контролера називається uptime. Пропущені перевірки не зменшують відсоток і можуть створювати враження повного покриття.
3. **Ручні перевірки змінюють статистику й автоматичний розклад.** SiteMonitor додає їх у денні лічильники, змінює consecutive_failures і next_check_at. Два ручні запуски можуть відкрити інцидент; часті ручні запуски зміщують наступну автоматичну перевірку.
4. **Падіння не сповіщається негайно.** Потрібні дві невдачі плюс доставка. За ідеального циклу у 5 хв це приблизно 5–10 хв від початку збою, але переповнений обхід/затримки cron можуть суттєво збільшити час. next_check_at задається від завершення перевірки, тому навіть фіксований cron може пропускати найближчий слот.
5. **Початок інциденту — друга невдача.** Тривалість від opened_at не включає час до підтвердження падіння. Немає окремих first_failed_at та detected_at.
6. **Немає повної аналітики періодів.** Картка виводить останні 30 записів денних підсумків і 30 інцидентів; немає перемикача періодів, часової шкали, тривалостей, агрегатів latency чи збереженого lifetime-підсумку.
7. **Загальна статистика залежить від кількості перевірок.** Активніше перевірюваний сайт сильніше впливає на загальний відсоток. Після очищення денних записів понад 365 днів повний lifetime-відсоток не відновити.
8. **response_ms — сумарний час виконання частини check, не TTFB і не браузерне завантаження.** Включає DNS/переходи/отримання відповіді та refresh моделі. DNS, TLS, connect, TTFB окремо не записані.
9. **Діагностика груба.** Більшість винятків об’єднано в одне повідомлення. Немає перевірки очікуваного контенту, строку TLS-сертифіката, попереджень про повільність.
10. **Моніторинг самого моніторингу обмежений.** Є попередження UI, якщо останній запуск старший за 15 хв. Немає окремого стану прострочення кожного сайту та зовнішнього сигналу про зупинку самого порталу.
11. **Перехід у «лише моніторинг» потребує окремої логіки.** toggleRemoteControl змінює прапорець і версію, але не відправляє ввімкнення. Раніше вимкнений дочірній сайт може залишитися вимкненим.
12. **Плановість накладається на HTTP-результат.** SiteMonitor ставить planned за підтвердженням команди навіть якщо фактичний GET успішний або має іншу проблему. Варто показувати окремо технічний результат та причину виключення зі статистики.
13. **Зміна URL зберігає історію під тим самим site_id.** SiteMetadataService скидає ключ/підтвердження керування, але не створює нову історію цілі перевірки. У звіті треба позначати зміну адреси.
14. **Одна точка спостереження.** Збій мережі порталу може виглядати як одночасне падіння багатьох сайтів. Дані не доводять глобальної доступності з усіх регіонів.

## 4. Запропоновані режими й налаштування

У формі: «Режим роботи» з двома описаними варіантами, типове значення — «Лише моніторинг». Для управління лишити наявне поле remote_control_enabled як єдине джерело правди; дублювати його окремим enum поки не потрібно.

Окреме налаштування «Автоматичні перевірки» визначає включення сайту в список cron. Пропозиція для міграції: monitoring_enabled=true для наявних Prod, false для Dev, щоб зберегти поточну поведінку. Для нових сайтів задавати значення явно. Можливість автоматично перевіряти Dev — налаштування, а не зміна всіх Dev без вибору.

Пропоновані параметри: інтервал, timeout у дозволених межах, поріг невдач, очікувані HTTP-коди; далі — контрольний URL і текст сторінки. Права на зміну параметрів узгодити з sites.write / monitoring.write. Developer не може увімкнути дистанційне керування підміною запиту; PM повинен мати шлях зміни дозволених йому параметрів без sites.write.

У режимі «лише моніторинг» сервер відхиляє disable/enable/sync; UI показує зрозумілу позначку. Для вже вимкненого керованого сайту перехід має вимагати успішного підтвердження ввімкнення або окремого явно описаного сценарію від’єднання. Мовчки залишати його заблокованим не слід.

## 5. Метрики та читабельний звіт

| Метрика | Що показувати | Етап |
| --- | --- | --- |
| Доступність | Поточний стан, час останньої перевірки, прострочення | Перший |
| Часова доступність | Відсоток за спостережуваний час і покриття періоду | Перший |
| Збої | Кількість, сумарна/максимальна тривалість, причина, відновлення | Перший |
| Швидкість | Середня, p95 і максимум за період, графік | Перший/другий залежно від зберігання |
| HTTP/помилки | Код, DNS/TLS/connect/timeout/HTTP/content, кінцева адреса | Другий |
| Сертифікат | Дата завершення, днів до завершення, попередження | Другий |
| Контент | Очікуваний текст або health endpoint для виявлення помилкових 200 | Другий |
| DNS/connect/TLS/TTFB | Окремі тривалості з транспортної телеметрії | Другий |
| CPU/RAM/диск/БД | Лише з окремою інтеграцією/агентом із правами лише на читання | Окреме розширення |

Звичайний HTTP GET не вимірює CPU/RAM, працездатність усіх бізнес-функцій або швидкість рендеру в браузері. Інтеграція серверних метрик не має вимагати дозволу вимкнення сайту.

Інтерфейс: «24 години / 7 днів / 30 днів / календарний місяць / увесь збережений період / власні дати»; за днями, тижнями й місяцями — відповідне групування. Картки: доступність, покриття, простій, інциденти, час відповіді. Нижче — шкала станів, графік часу відповіді та список інцидентів із тривалістю. Кожен відсоток має зрозумілий знаменник; порожня історія показує «немає даних», а не 100%.

Ілюстративний текст, не реальні дані: «За 7 днів: доступність 99,90%; 2 збої, приблизно 10 хв простою; середня відповідь 320 мс; покриття 100%».

## 6. Правила розрахунку

Потрібна оцінка часу за дискретними спостереженнями з чітко описаними межами точності.

- Зберігати час UTC; межі днів/тижнів/місяців будувати в обраній часовій зоні звіту. Початковий кандидат — Europe/Kyiv; перевірити чинні налаштування перед реалізацією.
- Розділити технічний стан, планове обслуговування та відсутність даних.
- Між послідовними регулярними вимірами застосовувати узгоджене правило оцінки стану. Якщо інтервал перевищує допустиме вікно, надлишок позначати unknown; не переносити останній up на багатогодинну зупинку cron.
- Зберігати першу невдачу та час підтвердження інциденту окремо. Для періоду брати перетин інтервалу збою з його межами, включно з відкритими інцидентами.
- Доступність без планових робіт = up_seconds / (up_seconds + down_seconds). Якщо знаменник нуль — «немає даних».
- Покриття = (up_seconds + down_seconds) / часу, який мав контролюватися поза плановими роботами. unknown, початок спостереження та паузи мають бути видимими окремо.
- Ручні перевірки зберігати для діагностики; пропозиція — не змінювати ними автоматичний розклад, часові агрегати й лічильник підтвердження автоматичного інциденту.
- Для загального показника порталу використовувати суму контрольованого site-time; середній відсоток сайтів показувати окремо й підписувати.
- Не усереднювати денні p95 для отримання місячного p95: потрібні збережені виміри або придатна до об’єднання гістограма. Середню рахувати через sum/count.
- Історичні checks дозволять лише обмежений перерахунок у межах наявних даних. Старі денні лічильники не містять тривалостей/latency; не вигадувати їх під час міграції.

## 7. Cron та сповіщення

Для швидшого виявлення пропонується cron щохвилини з індивідуальним next_check_at; для критичних сайтів інтервал 1 хв та підтвердження повторною перевіркою. Реальна досяжність залежить від кількості сайтів, затримок і хостингу. Це пропозиція, не вже налаштований розклад.

«Одразу» у періодичному моніторингу означає після виявлення. Перед реалізацією обрати політику: сигнал після першої невдачі (швидше, більше хибних тривог) або після короткої підтверджувальної перевірки. Зберегти відновлення, захист від дублювання, повтор доставки й аудит. Показувати причину, сайт, час початку, тривалість і посилання на інцидент. Для частих коливань додати обмеження повторів; планові роботи — окремо.

Одержувачі зараз глобальні. Наступний крок — відповідальні за сайт із глобальним резервним списком. Стан черги сповіщень, прострочені перевірки й ефективний інтервал мають бути видимими. Якщо портал повністю зупинений, сам себе через цей же cron він не сповістить: для цього потрібен незалежний зовнішній heartbeat.

Не збільшувати кількість паралельних HTTP без вимірювання навантаження. Спершу перевірити пропускну здатність послідовного обходу; потім за потреби обмежена конкурентність зі збереженням locks, SSRF-захисту й бюджету доставки.

## 8. Послідовність реалізації

1. **Режими й список перевірок.** Явний вибір, monitoring_enabled, права, міграція зі збереженням наявних режимів, правила переходу з блокованого сайту. Файли: SiteController, Site/Models/Site, SiteMetadataService, SiteControlService, маршрути й шаблони sites, нова міграція, RunMonitoring.
2. **Коректні виміри.** Відділити ручні запуски, записувати first_failed_at/detected_at, unknown/прострочення, часові агрегати й політику maintenance; розділити перевірку та агрегацію в сервісах Monitoring.
3. **Звіти.** Періоди, інциденти з тривалістю, денні/тижневі/місячні/довгострокові підсумки. Зберігати місячні/lifetime-агрегати перед видаленням деталей; показувати дату початку достовірної історії.
4. **Швидкі повідомлення й cron.** Налаштовувані пороги/інтервали, зрозумілий текст, відповідальні, видимість затримок доставки.
5. **Розширені метрики.** Сертифікат, контент, окремі мережеві фази; серверні метрики — окремим підключенням.

Великі часові звіти винести з контролера у сервіс статистики; сирі виміри та агрегати повинні мати одну визначену семантику. Не створювати другу систему паралельно до наявного Monitoring.

## 9. Критерії приймання майбутніх змін

- Сайт без дочірньої інтеграції додається в режимі моніторингу й перевіряється cron; дистанційні команди для нього відхиляються сервером.
- Наявні керовані сайти та їхні ключі/версії зберігаються після міграції; зміна режиму не залишає приховано вимкнений сайт.
- Вибір списку, Prod/Dev, soft delete, паузи, прострочення й права ролей перевірені.
- Ручний запуск не спотворює автоматичну статистику та розклад.
- На відомій часовій послідовності правильно рахуються up/down/planned/unknown, межі дня/місяця, перехід часу, відкриті інциденти та нуль даних.
- Падіння/відновлення/повтор Telegram не дублюють інциденти; права одержувача перевіряються перед доставкою.
- Очищення деталей зберігає погоджені довгострокові показники; міграція не приписує старим даним невідомі метрики.
- UI показує читабельні стани, тривалості, покриття й одиниці виміру.
- Тести на SQLite з підміною HTTP; міграції додатково перевірити на копії MySQL перед викладкою; робочі повідомлення й керування не потрібні для автоматичних тестів.

## 10. Що визначити під час перегляду

План можна починати з рекомендованих значень, але для фінальної конфігурації потрібні: приблизна кількість сайтів, бажана затримка сповіщення, чи потрібен автоматичний Dev, строк зберігання історії та відповідальні по сайтах. Рекомендований перший реліз: явні режими, список cron, чесна статистика з покриттям, періоди й повідомлення. CPU/RAM та браузерні перевірки не включати в базовий HTTP-моніторинг без окремої потреби.
