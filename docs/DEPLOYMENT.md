# Розгортання патчу порталу

Для патча моніторингу від 19 вересня актуальні параметри та розклад наведені в [MONITORING-PATCH.md](MONITORING-PATCH.md). Нижче — базова інструкція попереднього патча; її правило «лише Prod» та cron кожні 5 хв замінені новим патчем.

## Перед оновленням

- Зробити резервну копію бази, `.env` і попередньої версії коду. Зберегти чинний `APP_KEY`: ним зашифровані доступи сайтів, FTP і хостингів.
- Потрібні PHP **8.2+**, cURL, OpenSSL, PDO MySQL, mbstring та звичайні розширення Laravel. Приклад cron зі старим `php81` зі скріну не підходить цьому проєкту.
- Нові міграції **видаляють старі `domains`, `checks`, `settings`**. Список `sites` зберігається. Зворотна міграція поверне лише порожню стару структуру; старі дані відновлюються з резервної копії.
- Наявні неактивні користувачі переходять у `blocked`, оскільки неможливо надійно відрізнити давню реєстрацію від блокування. Адмін має переглянути їх. Нові реєстрації отримують `pending`.
- Пароль адміністратора не змінюється. **Не запускати загальний `db:seed`/UserSeeder на наявному проді.** Роль менеджера додає міграція.

## Послідовність

1. Прибрати старі cron `domains:check` та `portal:prune`. Узгодити коротке вікно оновлення порталу.
2. При копіюванні через FTP видалити лише застарілі файли з [REMOVED-FILES.txt](REMOVED-FILES.txt): просте накладання нових файлів залишає старі Artisan-команди. Викласти код, виконати `composer install --no-dev --optimize-autoloader`; зібрати ресурси через `npm ci && npm run build` або завантажити вже зібраний `public/build`.
3. У `.env` залишити справжні токени й usernames двох ботів. Налаштувати окремі `TELEGRAM_WEBHOOK_SECRET` і `TELEGRAM_SUPPORT_WEBHOOK_SECRET`: випадкові значення щонайменше 32 символи, наприклад 64 hex-символи. У локальному `.env` відсутні секрети вже згенеровано; цей файл не входить до Git. На проді їх треба перенести приватним способом або згенерувати окремо. BotFather видає **токен бота**, webhook-secret генерується самостійно.
4. Оновити кеш конфігурації і виконати міграції:

```bash
php artisan config:clear
php artisan migrate --force
php artisan config:cache
php artisan view:clear
php artisan route:cache
```

5. Зареєструвати webhook з новими секретами:

```bash
php artisan telegram:set-webhook
php artisan telegram-support:set-webhook
```

Команди перевіряють наявність секрету. Портал відхиляє запити webhook із відсутнім/неправильним секретом. URL за замовчуванням — `${APP_URL}/api/telegram/webhook` та `${APP_URL}/api/telegram/support/webhook`. `APP_URL` на проді має бути коректним HTTPS origin. Якщо раніше були явно задані `TELEGRAM_WEBHOOK_URL` / `TELEGRAM_SUPPORT_WEBHOOK_URL`, перевірити їх.

6. Активні Admin/PM/Developer підключають Access-бота з власного кабінету. Особисте посилання одноразове, на 15 хвилин. Старі невикористані посилання скидаються міграцією. Заблокований користувач та менеджер не отримують секретних доступів через Access-бота.
7. У «Моніторинг → Відповідальні» вибрати підключених активних Admin/PM. Без вибраних відповідальних історія перевірок працює, Telegram-сповіщень немає.
8. Додати один cron і перевірити його перший запуск. Підключення дочірніх сайтів описане в [CHILD-SITES.md](CHILD-SITES.md).

## Cron на хостингу «Україна»

У поле команди вставити фактичний шлях PHP 8.2+ та `artisan` цього проєкту:

```text
/шлях/до/php82/bin/php /home/ACCOUNT/PORTAL/artisan monitoring:run >> /home/ACCOUNT/monitoring.log 2>&1
```

Замінити всі шляхи на реальні з панелі. Розклад: `*/5 * * * *`. Обрати «Не запускати новий процес, якщо попередній ще працює». Постійний queue worker, Redis та WebSocket не потрібні. Використовувати `CACHE_DRIVER=file` на одному сервері; каталог `storage/framework/cache` має бути доступний для запису. Не використовувати `array` у продакшені: він не забезпечує блокування між процесами.

```dotenv
MONITORING_BATCH_SIZE=100
MONITORING_MAX_SECONDS=240
MONITORING_INTERVAL_MINUTES=5
MONITORING_PAUSE_MS=250
```

Команда послідовно перевіряє прострочені Prod, починаючи з тих, що найдовше чекали. Між сайтами є пауза, на HTTP-запит — тайм-аут 6 секунд, максимум 3 переходи. Після досягнення ліміту часу або кількості решта лишається для наступного запуску. Сповіщення теж мають обмежений бюджет. DNS, база та обмеження процесів хостингу можуть додати час; ліміт панелі має бути вищим за бюджет команди. Якщо хостинг примусово завершує PHP раніше — зменшити `MONITORING_MAX_SECONDS` і порцію, зберігши регулярний cron.

5 хвилин — цільовий інтервал, а не гарантія повного обходу 500 повільних сайтів. Перевіряти час останньої перевірки в таблиці. Для 100 сайтів почати з цих значень, далі налаштувати за фактичною тривалістю. Окремий `schedule:run` для цього модуля не потрібний.

## Моніторинг і повідомлення

- Автоматично перевіряються лише Prod; Dev доступні для ручної перевірки в картці та моніторингу.
- HTTP 2xx — доступний. Інші остаточні статуси/мережеві помилки — невдача. Інцидент і сповіщення створюються після двох послідовних невдач. Успішна перевірка закриває інцидент і додає повідомлення відновлення.
- Планове вимкнення враховується лише після підтвердження дочірнім сайтом поточної версії команди. Бізнес-статус «Заблоковано» не замінює команду вимкнення.
- Повідомлення об’єднуються в короткі групи; невдалі надсилання повторюються з паузою. Одержувачі перевіряються повторно перед доставкою. При невизначеному мережевому результаті Telegram можливий повтор повідомлення: гарантії exactly-once зовнішній API не дає.
- Детальні перевірки зберігаються 30 днів, денні підсумки — 365. Відсоток — частка успішних перевірок без планових вимкнень, не точний погодинний uptime. Журнал інцидентів зберігається для аналізу.
- Ручні перевірки не повинні використовуватися для навантаження сайтів; вони обмежені частотою та блокуванням одночасної перевірки одного сайту.

## Доступи й обмеження

Admin має всі права. PM читає портал, керує компаніями, підтверджує інших pending PM/Developer, керує сайтами й відповідальними моніторингу. PM не підтверджує себе, заблокованих або адміністратора. Developer додає/редагує сайти, компанії, статуси, FTP і хостинги; не керує вимкненням. Manager читає підтримку та відповідає на тікети; керування статусами тікетів і налаштуваннями залишається адміну. Менеджера активує адмін.

Публічні HTTP(S) адреси на портах 80/443 дозволені, приватні/службові IP та редиректи до них заборонені. Внутрішні dev-сервіси за замовчуванням заборонені; точкові винятки описані нижче. Для дистанційних команд потрібен HTTPS без редиректів. TLS-перевірка ботів не вимикається.

Кошик очищається остаточно лише явно адміністратором. М’яке видалення компанії не видаляє її сайти чи доступи.

## Перевірка й відкат

Локально: `php vendor/bin/phpunit` (PHP 8.2+, SQLite). Налаштування тестів примусово використовують SQLite `:memory:`, фіктивні токени й підмінені HTTP-запити. Робоча база не використовується.

Після викладки перевірити вхід ролей, підключення Access, відповідь підтримки, запуск cron, доставку повідомлення та тестове вимкнення/ввімкнення власного підключеного сайту. Повернення попереднього коду після міграцій робити разом із резервною копією бази та відповідними webhook-конфігураціями. Автоматичного запуску продових міграцій і реальних Telegram-повідомлень під час розробки патчу не було.


## Доповнення після перевірки патчу, 14 вересня

Нова міграція 2026_09_14_000001 додає журнал кожної спроби керування та стани обробки Telegram. Вона потрібна також тоді, коли попередні міграції патчу вже виконані. Історія спроб доступна в картці сайту: виконавець, версія, команда і результат. Старі спроби, яких раніше не зберігали, заднім числом не відновлюються. Вимкнення/увімкнення знову додаються в історію змін картки.

Після примусового завершення PHP наступний monitoring:run позначає попередній незавершений прогон перерваним. Перевірені сайти зберігають свій прогрес. Спроби керування без результату понад 15 хвилин позначаються перерваними; для них можна повторити синхронізацію (дочірній API захищений версіями). Строки зберігання задаються MONITORING_DETAIL_DAYS та MONITORING_DAILY_DAYS у .env.

### Перервані події підтримки

Webhook спочатку зберігає зашифровану подію й атомарно позначає її оброблюваною, а потім виконує логіку без загальної транзакції навколо Telegram-запитів. Повторний webhook не виконує вже почату подію знову. Завершені події звільняють збережений вміст. Якщо PHP обірвався або результат Telegram-запиту невідомий, подія потребує звірки. Це свідомо запобігає повторним повідомленням і темам: Telegram не має універсального ключа ідемпотентності для цих операцій.

На сторінці підтримки є попередження з кількістю таких подій. Cron виявляє події, що зависли довше 15 хвилин. Адміністратор у приватному терміналі виконує:

    php artisan telegram-support:review
    php artisan telegram-support:review --show=UPDATE_ID

Другу команду не направляти в cron/email/загальні логи: вона показує оригінальний текст клієнта. Звірити повідомлення/тему в Telegram з тікетом і клієнтом у порталі. Завершити відсутню відповідь вручну; якщо тема вже створена, зберегти її наявний thread ID замість створення дубля (за потреби через технічного адміністратора БД). Після звірки:

    php artisan telegram-support:review --resolve=UPDATE_ID

Команда resolve лише закриває перевірку й очищає збережений вміст, нічого не надсилає. Вона не повинна запускатися до звірки. Звичайну явно невдалу відповідь можна повторити в тікеті. Після тайм-ауту перед ручним повтором також перевірити, чи клієнт уже отримав повідомлення. Повернення недоставлених повідомлень до автоматичного повтору в цьому невизначеному випадку навмисно відсутнє.

### Винятки для внутрішніх сайтів

За замовчуванням усі внутрішні адреси заборонені. Якщо потрібен конкретний внутрішній dev-сайт, технічний адміністратор задає точний origin з портом та точні IP, наприклад:

    OUTBOUND_INTERNAL_TARGETS='{"https://dev.internal.example:443":["10.20.30.40"]}'

Після зміни виконати php artisan config:cache. Виняток дозволяє лише GET для цього origin і зазначених RFC1918/ULA адрес. DNS-зміна на інший приватний IP, інший hostname/порт/протокол, loopback, link-local і metadata-адреси лишаються заблокованими. Перенаправлення з іншого origin не отримує цей виняток. Команди керування з секретами до внутрішніх адрес не дозволяються. Для публічних dev-піддоменів винятки не потрібні.
