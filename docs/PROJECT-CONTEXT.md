# Контекст проєкту

Дата аналізу: 2026-09-19. Оновлено після реалізації [патча моніторингу](MONITORING-PATCH.md). Джерело — локальний код, міграції, шаблони, тести та наявні документи. Продакшен, робоча база, реальні боти й cron у цьому аналізі не перевірялися.

## Призначення й архітектура

Внутрішній портал обліку сайтів, компаній, хостингів, FTP-доступів, підтримки клієнтів, моніторингу й дистанційного керування. Це модульний Laravel-моноліт: модулі у `app/Modules`, серверні Blade-шаблони у `resources/views/portal`, переклади у `lang`.

Стек із маніфестів: PHP >=8.2, Laravel ^10.10, Guzzle, Sanctum, Laravel UI; Bootstrap 5, Vite 5, Chart.js 4. Наявність Chart.js не означає, що графіки моніторингу вже реалізовані.

`routes/web.php` та `routes/api.php` явно підключають маршрути модулів. `AppServiceProvider` реєструє конфігурації Monitoring, TelegramAccess і TelegramSupport. `app/Console/Kernel.php` реєструє команди. Документація розгортання орієнтується на PHP-хостинг і MySQL; фактичну робочу БД не перевірено. Тести використовують SQLite у пам’яті.

## Основні поняття

| Поле/сутність | Значення |
| --- | --- |
| Site / sites | Основний реєстр сайтів; компанія, статус, технічні параметри, доступи, soft delete |
| site_type | site / 3d / devbase: категорія проєкту |
| environment | prod / dev: середовище; автоматичні перевірки визначаються окремим monitoring_enabled |
| status_id | Бізнес-статус; не результат перевірки й не команда вимкнення |
| remote_control_enabled | Дозвіл надсилати дистанційні команди |
| is_active | Бажаний стан керованого сайту, не виміряна доступність |
| confirmed_state, confirmed_control_version | Останній підтверджений дочірнім сайтом стан і версія |
| monitoring_states.availability | unknown / up / down / planned |
| display_mode, embed_origins | Спосіб показу та дозволені origins для iframe |

Компанія має пов’язані сайти. FTP та акаунти хостингів можуть бути пов’язані з кількома сайтами. SiteRevision — історія змін картки; ActivityLog — аудит; site_control_attempts — історія окремих спроб керування.

## Права

Джерело: `app/Modules/Shared/Support/PortalAccess.php`, middleware маршрутів і модель User. Права залежать також від активності/погодження користувача.

| Роль | Основні можливості |
| --- | --- |
| Admin | Усі визначені портальні права |
| PM | Читання порталу, керування сайтами, моніторинг і відповідальні, частина операцій із компаніями та погодженням користувачів |
| Developer | Додавання/редагування сайтів, довідників і доступів; без sites.control та monitoring.read |
| Manager | Читання підтримки й відповіді |

PM має sites.control, але не sites.write: це важливо для нової форми. Developer може запустити перевірку через маршрут картки з sites.read, хоча не має доступу до розділу моніторингу.

## Основні потоки

1. Створення сайту: SiteController перевіряє дані, шифрує доступи/ключ, створює запис, ревізію та аудит. Команда керування автоматично не відправляється.
2. Керування: SiteControlService змінює бажаний стан/версію; SiteSyncService надсилає HTTPS-команду та перевіряє збіг підтвердженого стану й версії. Невдала доставка не доводить виконання команди.
3. Моніторинг: hosting cron → monitoring:run → SiteMonitor → SafeHttp → результати/денні лічильники/інциденти → записи сповіщень → Access-бот.
4. Підтримка: окремий Telegram webhook → inbox/обробник → клієнти, сесії, тікети й повідомлення → сервіс доставки відповідей. Staff-відповіді з Telegram-груп атрибутуються до підтверджених портал-користувачів через `users.telegram_chat_id`; відповідальні за напрям (`support_topic_user`) і фактичні виконавці в аналітиці розділені.

## Експлуатаційний контекст

- Керування потребує інтеграції дочірнього сайту; звичайний HTTP-моніторинг — ні. Див. [CHILD-SITES.md](CHILD-SITES.md) і каталог child-site.
- Дочірній сайт зберігає останній стан локально. Вимкнення дозволу керування в порталі не скасовує попереднє блокування.
- monitoring:run додатково позначає перервані операції підтримки та керування; зважати на це під час рефакторингу.
- [DEPLOYMENT-STATUS.md](DEPLOYMENT-STATUS.md) містить попередню нотатку про неналаштований cron. Це історичний запис, а не перевірений стан на дату аналізу.
- Міграція 2026_09_09_000003 виводить старі domains/checks/settings з експлуатації. Залишковий шаблон resources/views/checks не є основою нового моніторингу.
- Зберігати APP_KEY: ним зашифровані доступи. Не переносити секрети в документацію. На наявній базі не запускати загальний UserSeeder повторно.
